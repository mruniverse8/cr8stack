# Arena cost approval

Before launching competing Arena candidates, show the task, execution backend, candidate count, model and effort for each seat, maximum rounds, and whether a separate judge is included. Explain that each seat and judge consumes additional usage. Quote a monetary estimate only when supported by current account pricing and a stated workload estimate; otherwise say that the total cost is unknown.

Ask for explicit approval of that scope and wait. Selecting models in setup, invoking an architecture workflow, requesting a build, or granting general autonomy is not approval to launch the panel. An explicit approval already given for the stated candidates and judge covers both phases; do not ask again within that scope. A bare Arena request without an approved seat/round scope still needs the cost check.

The cross-judge pool is a list of eligible choices, not a command to launch every entry. Select at most the judge count the user approved, normally one. Before Phase C, check that the selected model, effort, backend, and judge seat were included. If not, request approval for the judge separately. If the judge is declined, do not launch it; report the omitted judgment and obtain any required decision about proceeding with coordinator-only selection.

Additional candidates, higher effort, a more expensive replacement model, another judge, a backend change, and reruns require new approval unless an explicit existing cap covers them. Record the approval and used scope in the task trail or saved plan so session recovery cannot silently enlarge it. Do not treat unknown pricing as proof that a substitution is cheaper.

This gate applies to Arena, including its use through architect and feature playbooks. If approval is absent, leave the Arena pass unstarted and state what waits. Do not evade the gate by renaming a competing panel as a swarm. It does not independently authorize any Cloud job, external publication, merge, or deployment.
